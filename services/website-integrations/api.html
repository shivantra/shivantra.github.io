API Integration

Connect Your Website With the Data and Services It Needs

Modern websites rarely operate alone. They may need product data from an ERP, appointments from a booking platform, payments from a payment provider or customer information from another application. Shivantra integrates websites and web applications with third-party and internal APIs so data and actions can move between systems reliably.

Request and response

The successful API call is only one part of the integration

A typical flow includes:

  1. Website collects or requests data
  2. Backend validates it
  3. Credentials are attached securely
  4. API request is sent
  5. Response is checked
  6. Data is transformed
  7. The website or internal system is updated
  8. Errors are logged

Integration types

Choose the pattern that fits the workflow

REST API

A common HTTP-based approach for reading and writing resources.

GraphQL

Useful where supported and where the client needs flexible access to a graph of structured data.

Webhooks

Useful when another platform needs to notify the website/backend that an event has happened.

Server-to-server integration

Useful for sensitive operations that should not expose credentials in the browser.

Scheduled synchronization

Useful when information can update periodically rather than in real time.

Authentication

Credentials belong on the server

APIs can use several authentication mechanisms:

  • API keys
  • bearer tokens
  • OAuth 2.x
  • signed requests
  • service accounts
  • custom token schemes

Implementation should follow the provider's supported method. Sensitive credentials should not be embedded in public frontend code.

Where user authorization is involved, token storage and refresh behavior should be designed carefully.

Data mapping

Two systems rarely describe the same data in exactly the same way

Website
  • firstName
  • lastName
  • phone
CRM API
  • given_name
  • family_name
  • mobile_number

The integration layer may need to:

  • rename fields
  • combine fields
  • normalize formats
  • convert dates
  • map enums
  • translate identifiers
  • remove unsupported values

Good mapping avoids silently corrupting or losing data.

Reliability

External systems fail sometimes. The integration should expect that.

Timeouts

Do not make visitors wait indefinitely for an external service.

Retries

Temporary failures may justify retrying, but repeated retries must be controlled.

Idempotency

A repeated payment or order request should not create duplicate transactions.

Rate limits

APIs often limit request frequency.

Caching

Read-heavy data may not need to be fetched for every page view.

Queues

Business-critical or slow work may be moved into background processing where architecture supports it.

Fallbacks

For non-critical integrations, the website may need a graceful fallback when a service is unavailable.

Security

Treat every integration boundary as a trust boundary

Implementation should consider:

  • input validation
  • server-side credentials
  • HTTPS
  • least-privilege scopes
  • secure token storage
  • file validation
  • webhook signature verification where supported
  • replay protection where relevant
  • logging without exposing secrets
  • endpoint rate limiting
  • dependency updates
