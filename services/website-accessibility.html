Website Accessibility

Make Your Website Easier for More People to Use

People experience websites in different ways. Some navigate with a keyboard. Some use screen readers. Some enlarge text. Some need stronger contrast, captions or clearer forms. Others may face temporary or situational limitations. Shivantra helps identify and remove accessibility barriers through design, development and remediation guided by WCAG 2.2.

Accessibility is about barriers

The same website can be easy for one person and difficult for another

A mouse-only interface may work perfectly for someone using a trackpad and fail for someone navigating by keyboard.

A light gray label may look elegant on one monitor and become unreadable for a user with low vision.

An icon-only button may be visually obvious but have no meaningful name for assistive technology.

Accessibility work looks for those barriers and improves the interface so more people can use it successfully.

That usually makes the website more robust and understandable for everyone.

WCAG 2.2

A practical framework for accessible web content

WCAG 2.2 provides testable success criteria under four principles.

Perceivable

Users need alternatives or presentation options that allow them to perceive information.

Examples include:

  • Text alternatives for meaningful images
  • Captions for relevant prerecorded media
  • Sufficient contrast
  • Content that can resize or reflow appropriately

Operable

Users need to navigate and use interactive elements.

Examples include:

  • Keyboard access
  • Logical focus order
  • Visible focus
  • Avoiding keyboard traps
  • Adequate target sizing where required
  • Alternatives to dragging interactions

Understandable

Content and interaction should be predictable and clear.

Examples include:

  • Meaningful labels
  • Clear error messages
  • Consistent help
  • Instructions for required input
  • Reducing unnecessary repeated entry

Robust

Code should expose correct semantics to browsers and assistive technologies.

Examples include:

  • Proper native HTML elements
  • Accessible names
  • Roles
  • States
  • Values
  • Valid custom component behavior
Common barriers

Accessibility issues often hide inside ordinary interface decisions

Keyboard navigation

Every interactive task should not require a mouse. We review:

  • Links
  • Buttons
  • Menus
  • Dialogs
  • Forms
  • Custom widgets

Images

Meaningful images need appropriate text alternatives. Decorative images should not create unnecessary screen-reader noise.

Forms

Forms need:

  • Labels
  • Instructions
  • Clear required states
  • Understandable validation
  • Associated error messages

Touch targets

Small or tightly packed controls can be difficult for people with limited dexterity or mobile users.

Media

Relevant audio/video may require captions, transcripts or other alternatives according to the content and conformance target.

Focus visibility

Keyboard users need to see where they are. Focus styles should be visible and should not be obscured by sticky headers, overlays or other content.

Semantic structure

Correct HTML improves both accessibility and maintainability. We review:

  • Headings
  • Landmarks
  • Lists
  • Buttons
  • Links
  • Tables
  • Form controls

Contrast

Text and meaningful interface components need sufficient visual contrast according to the target WCAG criteria.

Interactive components

Custom accordions, tabs, menus, dialogs and dropdowns need correct keyboard and assistive-technology behavior.

Motion

Animation and movement should not create unnecessary barriers and should account for reduced-motion preferences where applicable.

Automation is useful, but incomplete

An accessibility scanner cannot use the website like a person

Automated testing can detect some issues efficiently, such as:

  • missing attributes
  • certain contrast failures
  • duplicate IDs
  • some semantic problems

But many important questions require human judgment. For example:

  • Is the alt text actually meaningful?
  • Is the heading hierarchy logical?
  • Does the focus order make sense?
  • Can the modal be operated entirely by keyboard?
  • Is an error message understandable?
  • Does the interface still make sense at zoom?
  • Does a custom widget expose the right state?

For meaningful accessibility work, automated tools should be combined with manual testing and, where the project requires it, assistive-technology testing.

Remediation

Fix the cause, not only the scanner warning

Accessibility remediation can involve several disciplines.

Code

  • Replace clickable <div> elements with semantic controls
  • Correct labels
  • Manage dialog focus
  • Expose component state
  • Repair heading structure

Design

  • Improve contrast
  • Strengthen focus styles
  • Increase target size
  • Adjust layouts for zoom/reflow
  • Remove interactions that depend only on hover

Content

  • Improve link text
  • Rewrite instructions
  • Add useful alt text
  • Create captions
  • Clarify errors

A technically correct component can still be confusing, and good content cannot compensate for a broken keyboard interaction.

Accessibility needs to be considered across the complete experience.

Build accessibility into the design system

Reusable components can prevent the same issue from appearing on every page

For websites under active development, the best time to address accessibility is before inaccessible patterns spread. We can review and improve reusable components such as:

  • buttons
  • forms
  • navigation
  • cards
  • modals
  • tabs
  • accordions
  • tables
  • notifications

Once the component behaves correctly, many pages benefit at the same time.

This is often more sustainable than fixing isolated pages repeatedly.

Accessible forms

Forms deserve special attention

Forms are often where visitors are asked to complete an important task. Common barriers include:

  • placeholder-only labels
  • unclear required fields
  • errors shown only by color
  • focus not moving to relevant errors
  • inaccessible date pickers
  • time-limited interactions
  • authentication patterns that create unnecessary barriers

We design and remediate forms so the required action and any error recovery are understandable.

WCAG 2.2 conformance projects

Define the target before claiming conformance

If a project requires a formal WCAG target, the engagement should specify:

  • WCAG version
  • target level
  • pages/templates in scope
  • testing methodology
  • supported browsers/assistive technologies
  • known exceptions
  • remediation responsibilities
  • reporting format

Automated scans alone are not sufficient to establish full WCAG conformance.

Shivantra should not display a conformance claim unless the required evaluation has actually been completed and the claim remains accurate for the version of the site being referenced.

CMS and content accessibility

Developers are not the only people who can introduce accessibility issues

After launch, editors may add:

  • images
  • headings
  • links
  • tables
  • videos
  • downloadable documents

CMS configuration can make accessible publishing easier by:

  • exposing alt-text fields
  • limiting heading misuse
  • using controlled components
  • providing guidance
  • protecting key layout patterns

Editor training may also be useful where the team publishes frequently.
